## 1. Продукт и ключевая механика

Real-time аукционная платформа (Казахстан) для скоростной продажи недвижимости и авто.
Три роли: **Инвестор** (покупатель), **Продавец**, **Партнёр-риелтор**.

Лот проходит фазы: `Фаза I` (размещение, верификация, проверка реестров) → `Фаза II` (маркетинг, Open House, допуск участников и внесение задатков) → `Фаза III` (сами торги) → закрытие.

### Smart Hammer 50s — ядро системы

| Механика        | Правило                                                                                                                                                                                      |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Шаг ставки**  | Ровно **+3 %** от текущей цены. Других шагов нет. Сумму назначает сервер, не клиент.                                                                                                         |
| **Таймер**      | **50 000 мс**. Любая принятая ставка сбрасывает его обратно в 50 000 мс.                                                                                                                     |
| **Завершение**  | 50 секунд «тишины» → торги закрыты, статус `FINISHED`, генерируется официальный протокол.                                                                                                    |
| **Задаток**     | **10 %** от стартовой цены на спецсчёте. Без статуса `ON_SPECIAL_ACCOUNT` ставка не принимается.                                                                                             |
| **Blind ID**    | Участник виден как «Инвестор #704». Псевдоним уникален **в рамках лота** и меняется от лота к лоту — защита от картельного сговора. Реальные ФИО/ИИН/контакты в ленте не появляются никогда. |
| **Self-outbid** | Перебивать собственную последнюю ставку запрещено.                                                                                                                                           |
| **Rate limit**  | Не чаще 1 `place_bid` / 500 мс на session_id и на IP.                                                                                                                                        |
| **SLA Freeze**  | Если у >40 % клиентов лота деградация связи >2000 мс — таймер замораживается (снимок remaining), баннер + Push/SMS, авто-возобновление через 60 с.                                           |

**Главный риск проекта — гонки ставок.** Две принятые ставки на один шаг или потерянная ставка = юридический спор о деньгах. Отсюда правила раздела 4.

### Dev-окружение: без локального Docker

Решение сессии Phase 0: локальный Docker **не используем**.

- PostgreSQL — **локальный PG 17** на порту `5433`, база `auction`, аутентификация `trust`.
  Managed-Postgres для dev избыточен. TLS на localhost выключен сознательно (см. dev-setup).
- Redis — **локально, Redis 7.2 (Memurai Developer) на 6379**. Нативной сборки Redis под
  Windows нет, а служба требует прав администратора — поэтому пакет распаковывается
  административной распаковкой MSI в профиль пользователя и запускается обычным
  процессом (`docs/dev-setup.md`). Внутри настоящий Redis 7.2, поэтому Lua,
  миллисекундные TTL и pub/sub ведут себя один в один с продом. Managed (Redis Cloud)
  остаётся равноценной альтернативой.
- **Проверено фактически** (`pnpm check:env`): `EVAL` работает, `PTTL` отдаёт ровно
  50 000 мс, pub/sub round-trip 1 мс. Ядро Phase 3 на эти три вещи и опирается.
- **Ключи живут в пространстве имён** `REDIS_NAMESPACE` (`auction:` в разработке,
  `auction-e2e:` в тестах). Не косметика: e2e ходят в тот же инстанс, и без префикса
  прогон тестов вычищал бы рабочие ключи. `FLUSHDB` в коде и тестах запрещён.
- Подключение — только через строки в `.env`.
- **BullMQ: двоеточий в `jobId` быть не должно.** Сейчас проверка пропускает id ровно
  из трёх частей — совместимость со старым форматом, в коде BullMQ стоит пометка
  заменить её на прямой запрет. Разделитель — точка. Finisher (T-027) на этом
  подорвётся молча: очередь просто перестанет принимать задачи.
- **Расписание BullMQ даёт первый тик сразу при подъёме процесса**, а не через
  интервал. Поэтому у периодических задач должна быть защита от повтора (у крона
  ЕРД — метка суток в ключе задачи): иначе каждый рестарт воркера — это новый
  обход внешней госсистемы.

Dockerfile'ы в репозитории **есть и поддерживаются** — они нужны CI (сборка образов на GitHub-раннерах) и K8s в проде. ТЗ §1.1 этим не нарушается.

**Три процесса, один пакет.** `main.ts` (HTTP-API), `main.gateway.ts` (WS-сокеты),
`main.worker.ts` (фоновые задачи). В Kubernetes это три Deployment из **одного образа**,
различающиеся только командой запуска: профили нагрузки разные (gateway масштабируется
по числу соединений, API — по числу запросов), и падение одного не уносит остальные.

Отдельными пакетами их не разводим: код общий и останется общим — finisher торгов по
плану живёт сразу в `workers` и в `api/auction`, а gateway проверяет токены тем же
`TokenService`, что REST. Второй способ проверять подпись — второй способ её подделать.

**Корневой модуль процесса обязан импортировать `CryptoModule`**, хотя тот `@Global()`:
глобальным модуль становится, только будучи импортированным в контейнер. Забудешь —
процесс не поднимется на сборке `AuthService`, и узнаешь об этом при старте пода.

**Правило границ:** движок ставок (`auction`) ничего не знает о банках. Деньги ходят только через `deposits`/`payments`. Внешний мир — только через адаптеры в `integrations`, у каждого интерфейс + мок.

## 4. Правила работы

### 4.1. TypeScript

- `strict: true` везде. Плюс `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`.
- **`any` запрещён.** Недоверенный вход типизируется как `unknown` и сужается. Ослабление правила — только через явный `// eslint-disable-next-line` с комментарием «почему».
- Типы выводятся из Zod через `z.infer` — схема единственный источник истины.
- Union строковых литералов вместо `enum`.
- Экспортируемые сигнатуры аннотируем явно, локальные — выводим.

**Валидация — только Zod, второго стека нет.** REST-DTO, WS-события, переменные
окружения, любой внешний JSON. `class-validator` из проекта удалён сознательно:
критический путь — валидация `place_bid` по WebSocket, и два разных стека на денежном
пути означали бы два разных поведения на одних и тех же данных.

- DTO контроллера = `createZodDto(схема)` из `nestjs-zod`. Из одной схемы получаются
  и рантайм-валидация, и тип, и схема OpenAPI.
- Пайп регистрируется один раз в `AppModule` через `APP_PIPE`, а не в `main.ts`:
  тогда e2e-тесты, поднимающие модуль, гоняют ровно те же правила, что прод.
- **Каждая схема запроса — `.strict()`.** Zod по умолчанию молча выбрасывает лишние
  ключи, а нам нужен отказ (аналог `forbidNonWhitelisted`): попытка протащить лишнее
  поле в ставку обязана быть видна, а не проглочена (QA-04).
- **`z.bigint()` в схемах запросов и ответов запрещён.** `z.toJSONSchema()` на нём
  падает с `BigInt cannot be represented in JSON Schema`, и `/docs` перестаёт
  открываться целиком. Деньги на проводе — целые тенге (`z.number().int()`),
  `bigint` живёт только внутри и конвертируется на границе.

### 4.2. Деньги

> **Никогда не `float`. Ни одной операции с деньгами в `number` с дробной частью.**

- Хранение и все вычисления — **целые тиыны** (1 тенге = 100 тиын), тип `BIGINT` в PostgreSQL, `bigint` в TypeScript.
- **Денежные колонки называются `*_tiyn`, а не `*_kzt`** (набросок в §6 плана использует `_kzt`).
  Единица измерения обязана быть видна в имени: денежные ошибки рождаются ровно из
  вопроса «а это тенге или тиыны?».
- **Округление шага +3 %:** банковское округление (half-to-even) **до целого тенге**. Правило зафиксировано планом (T-024) и не меняется без пересмотра плана. Следствие: цена в тиынах всегда кратна 100.
- **Задаток округляется ВВЕРХ до целого тенге**, а не банковским округлением, как шаг.
  Десятая часть цены в тиынах не обязана быть кратной тенге (лот за 1005 ₸ даёт 100,5 ₸),
  а на провод уходят целые тенге — такая сумма там непредставима. Вверх, потому что
  шаг это цена и в ней важна симметрия, а задаток — гарантия: недобор недопустим,
  лишний тенге вернётся вместе с задатком.
- **Провод (WS/REST):** наружу отдаём **тенге**, потому что ТЗ §2.1 задаёт `current_price_kzt: 46350000`. Конвертация — только на границе, в сериализаторе. Внутрь тенге не проникают.
- Сумму ставки считает **сервер**. Присланная клиентом сумма — не источник, а проверка: если `bid_amount ≠ round(current_price × 1.03)` на момент обработки — отказ `PRICE_MISMATCH` (QA-04).
- **Правило шага существует в одном экземпляре — в `auction/lua/primitives.ts`.**
  Оттуда его берут и приём ставки, и снимок состояния, который называет клиенту
  сумму следующего шага. Вторая реализация «+3 %» — это второй ответ на вопрос,
  сколько человек должен заплатить: участник посчитает по своей, сервер сверит по
  своей, и честная ставка получит отказ. В `apps/web` осталась витринная функция
  для лотов **до** старта торгов — она помечена и на провод не идёт.
- Шаг считается **в целых числах** (`tenge * 103`, затем деление на 100 с разбором
  остатка), а не умножением на `1.03`: множитель не представим двоичной дробью
  точно. Граница точности Lua — 2^53 ≈ 9·10^15, верхняя цена лота 10^14 тиын,
  запас ~90×.
- **Отказ по ставке обязан называть актуальную цену и сумму следующей ставки.**
  Считает их тот же Lua-скрипт, который отказал, — вторым обращением в Redis
  нельзя: отказ в гонке это 99 путей из 100, и лишний round-trip означал бы, что
  чем острее борьба за лот, тем медленнее система. Без цены в отказе проигравший
  переспрашивает состояние отдельным запросом, и сотня одновременных ставок
  превращается в сотню лишних запросов ровно в самый нагруженный момент лота
  (найдено харнессом T-052). Цены нет только у `NO_SESSION` — у лота без торгов
  её не существует, и подставлять ноль нельзя: ноль уедет участнику на кнопку.

### 4.3. Источники истины

| Что                                                     | Кто авторитет  | Почему                                                   |
| ------------------------------------------------------- | -------------- | -------------------------------------------------------- |
| Цена, дедлайн, seq, статус торгов **во время сессии**   | **Redis**      | Миллисекундные операции и атомарность на 50 000 клиентов |
| Деньги, ставки как аудит, пользователи, лоты, документы | **PostgreSQL** | Append-only аудит, транзакции, юридическая доказуемость  |

- Синхронизация Redis → PG через **outbox + идемпотентные обработчики**. Не двойная запись «в обе стороны».
- **Одна неисправимая запись в outbox останавливает перенос ставок целиком.** Пачка
  пишется одним `createMany`; запись о ставке по несуществующему лоту валит её на
  внешнем ключе, и пачка повторяется бесконечно. Новые ставки при этом не доезжают в
  PostgreSQL вообще, а выглядит это как «лента пустая». Найдено на браузерном стенде,
  где база пересоздаётся, а поток в Redis — нет. В проде лоты не удаляют, но карантин
  для навсегда сбойных записей всё равно нужен — иначе очередь встаёт молча.
- `bids` и `audit_log` — **append-only**, и это не соглашение, а ограничение БД:
  триггеры запрещают `UPDATE`, `DELETE` и `TRUNCATE`. Действует на любой путь записи,
  включая ручной `psql`. Пересоздание схемы (`migrate reset`) не блокируется.
- **Единственное исключение — база с именем на `_test`.** Оно записано в самой функции
  триггера и проверено фактически: в `auction` и `DELETE`, и `TRUNCATE` отклоняются, в
  `auction_test` проходят. Без исключения очистка между тестами невозможна в принципе:
  на ставку по внешним ключам висят сессия, лот и участник, значит неудаляемы и они —
  и после первого же теста, дошедшего до торгов, соседние видели бы чужие лоты в
  каталоге. Условие нельзя обойти из приложения: имя базы не подделать, в отличие от
  флага или переменной сессии.
- **Цена точна, пока не превышает 2^53 тиын (~90 трлн ₸).** Шаг +3 % возводится в
  степень: от миллиона тенге граница достигается примерно на шестисотой ставке подряд
  по одному лоту. Дальше система не ошибается в деньгах — она перестаёт принимать
  ставки (`PRICE_MISMATCH`), потому что цена перестаёт совпадать сама с собой после
  round-trip через строку. Отказ безопаснее тихой ошибки, но знать про границу нужно.
- Дедлайн торгов авторитетен как `deadline_at`, а не как TTL ключа. **Redis key-expiry — только страховка**, не источник истины: активный finisher решает, завершены ли торги (иначе GC-пауза = спорный финиш).
- **Время — только серверное.** Клиентские часы не участвуют ни в чём. Все события несут `server_ts`; клиент получает `time_remaining_ms`, а не абсолютное время.
- **`Date.now()` в бизнес-логике не вызываем** — только через `TimeService`. Интервалы
  (дедлайны, остаток таймера, длительность сессии) считаются по `monotonicMs`: стенные
  часы прыгают от NTP и пауз виртуалки, и прыжок назад посреди торгов воскресил бы
  уже завершённый аукцион.
- **Внутри торгов часы одни — часы Redis (`TIME`).** Правило выше работает в пределах
  одного процесса, а процессов много: API-инстансы, gateway, воркеры, и общего
  монотонного счётчика у них нет. Дедлайн вычисляется в Redis, хранится в
  Redis-времени и сравнивается с `TIME` внутри того же атомарного скрипта, что и
  ставка. Дрейф между узлами держит chrony (NFR-04). Считать «сейчас» в Node и
  присылать его в скрипт нельзя: два инстанса с расхождением в 200 мс дадут два
  разных ответа на вопрос «успел ли участник».
- **В Lua большие числа печатаются через `string.format('%.0f')`.** `tostring()` на
  миллисекундах эпохи даёт `1.786e+12`, и дедлайн превращается в мусор молча.
- **Статус `PHASE_III` не выставляется сменой статуса** — только через старт торгов
  (`POST /api/admin/lots/{id}/auction/start`). Лот в торгах без сессии — это цена,
  дедлайн и seq, которых не существует: в каталоге он выглядит живым, а поставить
  на него нельзя.
- Весь REST — под префиксом `/api`: ingress отдаёт `/api` в API, `/` в web.

### 4.4. База данных

- **Только миграции.** Схему руками в БД не трогаем — ни в dev, ни где-либо ещё. Изменение схемы = файл миграции в репозитории.
- `migrate:up` / `migrate:down` идемпотентны на чистой БД.
- DDL и backfill данных — **разными** миграциями.
- Не добавляем `NOT NULL` без `DEFAULT` в существующую таблицу: сначала nullable → backfill → constraint.
- Индексы в проде — `CREATE INDEX CONCURRENTLY` (нельзя внутри транзакции).
- Переименования — expand-contract, дроп колонки только после выката кода без ссылок на неё.
- **`updateMany` в Prisma 7 проставляет `@updatedAt`** — вопреки распространённому
  утверждению, что не проставляет. Проверено тестом на `updated_at` (T-017). Если
  правка не должна выглядеть изменением сущности (счётчики, служебные поля) — только
  явный `$executeRaw`. Значение `updated_at` видит продавец, и «изменён минуту назад»
  оттого, что кто-то открыл карточку, — это ложь в интерфейсе.

### 4.5. ПДн и безопасность

- ФИО, ИИН, телефон, email — **только в зашифрованных колонках** (AES-256-GCM, ключ вне БД).
  Всё идёт через `PiiCryptoService`, руками `createCipheriv` нигде не вызываем.
- Каждый шифротекст привязан к своей колонке через AAD (`users.iin`, `users.phone`, …):
  блоб, переставленный в другую колонку, не расшифруется. Заводишь новое поле с ПДн —
  добавь его в `PiiPurpose`.
- Поиск по ИИН — через blind index (HMAC отдельным ключом), не через расшифровку таблицы.
  Ключ индекса **обязан** отличаться от ключа шифрования: его утечка компрометирует
  поиск, но не сами данные.
- Два ключа в env, оба ровно 32 байта, проверяются на старте. В проде — из KMS.
- Из хендлеров **не возвращаем сущности ORM** — только явные response-DTO. Сырая сущность утечёт `pii_enc`, токены, служебные колонки.
- Глобальный `ValidationPipe` (`whitelist` + `forbidNonWhitelisted` + `transform`) настраивается один раз в `main.ts`; e2e гоняются на тех же пайпах/фильтрах/гвардах, что и прод.
- Грубые проверки доступа — в гвардах; владение ресурсом — в сервисах.
- **По умолчанию закрыто всё**: JwtAuthGuard и RolesGuard глобальные, открытая ручка
  помечается явным `@Public()` — такое место видно в диффе. Роли гвард читает из БД,
  а не из токена: блокировка и понижение прав действуют немедленно.
- Refresh-токены: в БД только SHA-256-хэш; ротация с обнаружением повторного
  использования — предъявление потраченного токена гасит всё семейство сессий.
- e2e поднимают приложение через `configureApp()` из `app.setup.ts` — ту же функцию,
  что и prod. Меняешь пайп/фильтр/префикс — меняй там, иначе тесты проверяют не то
  приложение. Тестовая БД обязана оканчиваться на `_test` (защита в test-db.ts).
- **Адрес клиента — только через `TRUST_PROXY_HOPS`** (число прокси перед API), не через
  `trust proxy: true`. `X-Forwarded-For` дописывает кто угодно, включая самого клиента:
  при доверии всему заголовку Express возьмёт самую левую запись — присланную клиентом.
  На адресе держатся антинакрутка просмотров и лимит ставок (FR-10).
- **Метрики отдаются на своём порту (`METRICS_PORT`), а не ручкой в `/api`.**
  Ingress публикует наружу весь префикс `/api`, и метрики в нём означали бы, что
  размеры комнат, поток ставок и разбивка отказов по кодам доступны любому. Этого
  порта в ingress нет вовсе. В Kubernetes порт один на все три процесса (у каждого
  свой под); на одной машине им нужны разные значения — процесс, которому порт
  занят, не поднимется, и это правильно: молча оставшийся без метрик процесс на
  дашборде выглядит как «всё спокойно».
- Никаких секретов в репозитории. Только `.env.example` с пустыми значениями.

### 4.6. Процесс

- **Одна задача T-XXX за раз.** Не забегаем вперёд по фазам, даже если «логично сразу».
- **Статусная машина лота** — таблица в `lots/lot-status.machine.ts`, единственный
  источник истины о переходах. Новый переход = правка таблицы + юнит-снимка, не if в сервисе.
- **Адаптеры внешних систем** (`integrations/*`): интерфейс + DI-токен + мок. Потребители
  зависят только от интерфейса; реальная реализация подключается заменой провайдера.
- **Инварианты — в БД, где возможно**: append-only триггеры, уникальные ключи
  (двойная ставка, двойная запись на показ, двойной сплит). Код проверяет, БД гарантирует.
- Тестовая БД чистится только через `cleanDatabase()` из `test/test-db.ts` (FK-порядок).
  Тесты, создающие ставки, работают на уникальных данных — bids не удаляемы.
- Требование в плане непонятное или противоречивое — **спросить**, а не додумать. Все допущения живут в разделе 3 плана (ОВ-1…ОВ-12).
- Новая зависимость ставится только с объяснением, зачем она.
- **Работает > красиво.** Инфраструктура поднимается одной командой.
- Формат коммита: `тип(T-NNN): описание` — conventional commits + ID задачи в scope.
  Типы: `feat`, `fix`, `chore`, `ci`, `test`, `docs`, `refactor`, `perf`.
  Пример: `chore(T-005): каркас NestJS`
  Scope необязателен, но если есть — обязан быть ID задачи вида `T-004`.
  Проверяется автоматически (commitlint), обойти нельзя.
- Хуки (husky), обойти которые = обойти ревью:
  - `pre-commit` — Prettier форматирует изменённые файлы, затем ESLint с `--max-warnings 0`.
    Ошибка линтера (например `any`) **отклоняет коммит**, файлы откатываются.
  - `commit-msg` — commitlint проверяет формат сообщения.

## 5. Команды

```bash
pnpm install          # установка (Node 22+, pnpm 11+)
pnpm check:env        # проверить коннект к managed PG/Redis (+ Lua, PTTL, pub/sub)
pnpm dev              # api + web в watch-режиме
pnpm build            # сборка всех пакетов воркспейса
pnpm test             # юнит + интеграционные
pnpm test:browser     # приёмка в браузере (Playwright): поднимает свой стенд на 3110/3210/3111
pnpm lint             # ESLint (правила с учётом типов)
pnpm lint:fix         # ESLint с автоправками
pnpm format           # Prettier: отформатировать
pnpm format:check     # Prettier: только проверить
pnpm typecheck        # tsc --noEmit по всем пакетам
pnpm db:migrate       # накатить миграции
pnpm db:studio        # Prisma Studio
```

**Docker в dev не нужен** — PostgreSQL и Redis managed (см. раздел 2). `docker compose` в этом проекте не является путём разработки; образы собирает CI, разворачивает Kubernetes.

Первый запуск и получение строк подключения — [docs/dev-setup.md](docs/dev-setup.md).

## 6. Чеклист перед коммитом

1. `pnpm lint` — зелёный.
2. `pnpm typecheck` — зелёный, `any` не добавлен.
3. `pnpm test` — зелёный. Для найденного бага есть regression-тест.
4. Деньги: ни одного `float`/`number` в денежных вычислениях, всё в тиынах (`bigint`).
5. Схема БД менялась? — есть файл миграции, руками БД не правили.
6. ПДн: новые поля с ФИО/ИИН/телефоном зашифрованы, из хендлеров не возвращаются сущности ORM.
7. Секреты: в диффе нет ключей, паролей, строк подключения. `.env` не в индексе.
8. DoD задачи из `docs/DEVELOPMENT_PLAN.md` проверен фактическим прогоном, а не «на глаз». Что проверить не удалось — сказано явно.
9. Задача отмечена `[x]` в `docs/TASKS.md`.
10. Сообщение коммита: `тип(T-NNN): описание`.
