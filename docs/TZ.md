**ПЛАТФОРМЫ «ЦИФРОВОЙ ГИБРИДНЫЙ АУКЦИОН СКОРОСТНЫХ ПРОДАЖ»**

*(System Architecture & Functional Requirements Protocol)*

**📍 РАЗДЕЛ 1. СТАК ТЕХНОЛОГИЙ И ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ К СИСТЕМЕ**

- **1.1. Рекомендуемый стек технологий**

- **Frontend:** React.js / Next.js (SSR для высокого SEO и мгновенной загрузки), Tailwind CSS, Redux Toolkit / Zustand.

- **Backend:** Node.js (NestJS) / Go (Golang) — для высоконагруженных WebSocket-соединений и микросекундного отклика.

- **База данных (DBMS):** PostgreSQL (основная реляционная БД для финансов, пользователей и лотов), Redis (In-Memory БД для кэширования, управления WebSocket-сессиями и работы секундомера в реальном времени).

- **Real-time протокол:** **WebSocket (WSS)** с fallback на Server-Sent Events (SSE) / Long Polling.

- **Инфраструктура & Cloud:** AWS / Hetzner / NGINX Load Balancer, Kubernetes / Docker containers.

- **Безопасность и CDN:** Cloudflare Enterprise (Anti-DDoS, WAF), Biometric CloudPayer (защита от скриптов/ботов).

- **1.2. Требования к производительности и отказоустойчивости**

- **Ping / Latency:** Задержка передачи данных по WebSocket при совершении ставки — **не более 15 миллисекунд (\<=15ms)**.

- **Нагрузка (Concurrent Users):** Выдерживание одновременных подключений до **50 000 активных пользователей** на один Лот без просадки FPS и рассинхронизации таймера.

- **Time Synchronization:** Синхронизация системного времени сервера с NTP-серверами (Network Time Protocol) с точностью до **1 миллисекунды (0.001s)**. Время на клиенте (смартфоне/ПК) не влияет на таймер!

    **⚙️ РАЗДЕЛ 2. ЯДРО СИСТЕМЫ: АЛГОРИТМ SMART HAMMER 50s**

┌─────────────────────────────────────────────────────────────────────────┐

│ ЛОГИКА РАБОТЫ МОДУЛЯ SMART HAMMER 50s (REDIS) │

├─────────────────────────────────────────────────────────────────────────┤

│ 1. Инициализация Фазы III -\> Установка ключа Redis: TTL = 50.000 ms │

│ 2. Старт вещания через WebSocket -\> Broadcast \[Current Price, TTL\] │

│ 3. Валидация входящего клика \`+3%\` в обработчике Redis Transaction │

│ 4. При успехе: │

│ • Current Price = Current Price * 1.03 │

│ • Сброс ключа Redis: TTL = 50.000 ms │

│ • Broadcast всем подключенным клиентам нового состояния (P2P) │

│ 5. При TTL == 0 -\> Вызов событийного Триггера Event: AUCTION_FINISH │

└─────────────────────────────────────────────────────────────────────────┘

- **2.1. Пошаговый сценарий работы обратного таймера (00:50)**

1.  **Инициализация:** При старте Фазы III сервер создает топик WebSocket для конкретного Лота и инициализирует таймер обратного отсчета на **50.000 миллисекунд**.

2.  **Тиканье таймера:** Каждую секунду (1000 ms) сервер транслирует через WebSocket сокет-событие timer_tick всем подключенным веб- и мобильным клиентам.

3.  **Обработка входящей ставки +3%:**

  - Когда участник нажимает кнопку **«Сделать ставку +3%»**, клиент отправляет WebSocket-событие place_bid с JWT-токеном пользователя и ID Лота.

  - **Серверная валидация:** Сервер проверяет:

        1.  Активен ли таймер (TTL \> 0);

        2.  Наличие на депозитарном счете пользователя 10% задатка;

        3.  Не является ли ставка попыткой перебить *собственную* последнюю ставку.

  - **Сброс таймера:** При успехе валидации Redis выполняет атомарную операцию: **Current_Price = Current_Price + 3%** и переустанавливает TTL таймера обратно в положение **50.000 ms**.

  - **Broadcasting (Рассылка):** За **\<5 ms** сервер отправляет всем подключенным клиентам событие bid_updated со следующей структурой JSON:

JSON

{

\"event\": \"bid_updated\",

\"lot_id\": \"LOT-8801-KZ\",

\"current_price_kzt\": 46350000,

\"bid_step_kzt\": 1350000,

\"last_bidder_blind_id\": \"Инвестор #704\",

\"time_remaining_ms\": 50000,

\"timestamp\": 1785934667000

}

4.  **Завершение торгов (Smart Hammer Trigger):**

  - Если в течение 50.000 ms с момента последней ставки не поступило ни одного валидного события place_bid, Redis генерирует событие key_expired.

  - Сервер моментально блокирует прием любых последующих ставок, переводит статус Лота в FINISHED и выполняет команду generate_official_protocol().

  - Все клиенты получают всплывающий модальный блок: **«ТОРГИ ЗАВЕРШЕНЫ. Победитель: Инвестор #704»**.

- **2.2. Протокол SLA Freeze (Защита от сетевых сбоев и DDoS)**

- **Мониторинг соединения (Heartbeat):** Сервер раз в 2 секунды отправляет Ping-пакет всем клиентам.

- **Триггер заморозки:** Если потеря пакетов или задержка сокета у более чем 40% подключенных пользователей превышает 2000 ms (серверный или провайдерский сбой), сервер автоматически переводит торги в статус SLA_FREEZE.

- **Логика SLA Freeze:**

  - Таймер ставится на паузу (TTL замораживается);

  - На экране всех пользователей высвечивается статус: *«Внимание! Сетевая пауза (SLA Freeze). Торги возобновятся через 60 секунд»*;

  - Всем участникам отправляется приоритетное Push/SMS-уведомление.

        **🔒 РАЗДЕЛ 3. МОДУЛЬ АНОНИМИЗАЦИИ (BLIND ID) И АНТИФРОД**

- **3.1. Логика генерации Blind ID**

- Во избежание картельного сговора реальные ФИО, ИИН и контакты участников **строго зашифрованы** на уровне базы данных.

- При входе верифицированного пользователя в торги по конкретному Лоту Backend генерирует уникальный псевдоним Blind ID по формуле:

Blind_ID = \"Инвестор #\" + Hash(User_ID + Lot_ID).slice(0, 3).

- Пример отображения в чате ставок: Инвестор #104, Инвестор #882. Идентификатор меняется от Лота к Лоту.

- **3.2. Защита от авто-кликеров и ботов**

- **Rate Limiting:** Ограничение на количество отправляемых запросов place_bid — не более **1 клика в 500 миллисекунд** от одного IP/Session ID.

- **Biometric CloudPayer:** Анализ микро-движений курсора мыши / сенсорного нажатия перед отправкой события ставки. Если клик произведен без фиксации движения пальца/курсора (признак бота), запрос мгновенно блокируется с выдачей Captcha.

- **4.1. Спецификация Личного Кабинета Инвестора (Покупателя)**

- **Виджет 10% Задатка:**

  - Показ статуса гарантийного взноса: \[Заморожено / На Спецсчете\];

  - Кнопка быстрых инвойсов (IBAN) / Банковский Hold эквайринг;

  - Таймер обратного отсчета SLA 24h до авто-возврата средств при проигрыше.

- **Интерфейс Торгов (Аукционный зал):**

  - Большая динамическая кнопка: **«СДЕЛАТЬ СТАВКУ \[Текущая цена + 3%\]»** (меняет цифровое значение в реальном времени);

  - Крупный таймер 00:50 с цветовой индикацией (Зеленый 50-20 сек -\> Желтый 20-05 сек -\> Красный 05-00 сек);

  - Лента истории ставок (Real-time feed).

- **Модальное окно Runner-Up (Участник №2):**

  - Появляется при завершении торгов, если пользователь занял 2-е место.

  - Две кнопки-триггера:

        1.  \[Активировать Опцию «А»: Сохранить задаток на 5 дней для выкупа при дефолте №1\];

        2.  \[Активировать Опцию «Б»: Забрать 100% задаток за 24 часа\].

- **4.2. Спецификация Личного Кабинета Продавца**

- **Монитор прозрачности:**

  - Отображение счетчика просмотров Лота, количества скачиваний Сертификата СпецСТО / Data Room;

  - График записи покупателей на «Open House» (5 дней).

- **Дашборд Очного Этапа:**

  - Live-трансляция торгов на Фазе III без права совершения ставок.

- **Управление Кнопкой ВЕТО:**

  - По окончании Фазы III активируется блок выборки: \[Подтвердить продажу и сделку\] или \[Активировать ПРАВО ВЕТО\].

  - При клике на ПРАВО ВЕТО система автоматически генерирует и выводит на экран готовый для подписи **«Акт реализации Права ВЕТО и Цифрового Карантина» (Приложение №3)** с таймером наложения Lockout на 5 месяцев.

- **4.3. Спецификация Личного Кабинета Партнера (Риелтора / Брокера)**

- **Lead Protection CRM-Трекер:**

  - Форма быстрой регистрации Лида (ИИН/Телефон собственника + Кадастровый номер/VIN);

  - Авто-проверка по базе: если Лид свободен, система выдает статус \[ЗАКРЕПЛЕН ЗА ВАМИ НА 90 ДНЕЙ\];

  - Прогресс-бар движения объекта по Фазам (Фаза I -\> Фаза II -\> Фаза III -\> Закрытие).

- **Финансовый модуль Ref-Bonus:**

  - Автоматический калькулятор: Прогнозируемый бонус = Текущая победная цена * 2%;

  - История выплат с уведомлением о поступлении комиссии на расчетный счет.

        **🏛️ РАЗДЕЛ 5. ИНТЕГРАЦИЯ С ВНЕШНИМИ СЕРВИСАМИ И БАНКОВСКИМ КОНТУРОМ**

- **5.1. Интеграция с Государственными реестрами РК**

1.  **Digital ID / Спецкод / eGov Mobile API:** Авторизация и верификация пользователей через сканирование QR-кода eGov или биометрию (Facial Recognition).

2.  **Интеграция с КИСИП / ЕРД (Реестр должников и арестов):** Автоматический REST API запрос по ИИН/БИН и Кадастровому номеру/VIN при создании Лота и раз в 24 часа. При возврате статуса HAS_RESTRICTION = true Лот автоматическ переводится в статус PAUSED.

- **5.2. Интеграция с Банковским Депозитарным контуром (Счет Б)**

- **Автоматическое расщепление платежей (Payment Splitter):** При поступлении 90% доплаты от Победителя банковский API автоматически отправляет 5% комиссии на Операционный счет ТОО (Счет А), задолженность залогодержателю — на ссудный счет банка, а чистый остаток — Продавцу.

- **Auto-Refund Webhook:** При команде TRIGGER_REFUND (для непобедивших) сервер отправляет банковскому API платёжное поручение со Специального депозитарного счета с формированием КБЕ и назначения платежа без НДС.

    **📋 РАЗДЕЛ 6. ЧЕК-ЛИСТ ПРИЕМКИ И ТЕСТИРОВАНИЯ (QA & ACCEPTANCE)**

Для сдачи проекта IT-разработчиками должны быть успешно пройдены следующие авто-тесты:

- [ ] **Load Test:** Проливка 50 000 виртуальных сокет-клиентов на 1 Лот. Таймер не останавливается, лаг не превышает 15ms.

- [ ] **Concurrency Test:** Одноновременный клик +3% от 100 пользователей в одну миллисекунду. Система берет ровно ОДНУ первую ставку, остальным выдает обновленную цену.

- [ ] **Disconnection Test:** Отключение интернета на стороне клиента во время таймера. При переподключении UI моментально синхронизирует время с сервером.

- [ ] **Security Test:** Попытка подмены суммы ставки через DevTools/Postman. Backend отклоняет любой запрос, где Bid_Amount != Current_Price * 1.03.
