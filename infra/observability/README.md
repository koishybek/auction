# Наблюдаемость: метрики, дашборд, алерты (T-053)

Приёмка по латентности требует чисел, а не ощущений. Здесь ровно то, чем эти
числа берутся.

## Что где

| Файл                                | Что                                                 |
| ----------------------------------- | --------------------------------------------------- |
| `prometheus/auction.rules.yml`      | записывающие правила (квантили) и 8 алертов         |
| `prometheus/auction.rules.test.yml` | юнит-тесты правил: деградация задаётся рядами чисел |
| `prometheus/scrape.example.yml`     | образец конфигурации сбора по аннотациям подов      |
| `grafana/auction-dashboard.json`    | дашборд: 8 панелей, пороги нанесены на графики      |

## Как проверить, не поднимая кластер

```bash
promtool check rules prometheus/auction.rules.yml
promtool test rules prometheus/auction.rules.test.yml
```

Второе — это и есть DoD «алерт срабатывает на синтетической деградации».
**Проверены все восемь алертов**: ставка в пределах SLA молчит, ставка в 50 мс
поднимает алерт (и не раньше, чем истечёт `for` — алерт от одной точки будил бы
людей на всплеске), вещание в 10 мс поднимает свой, деградация связи у половины
клиентов предсказывает SLA Freeze, остановка тиков ловится при непустых
комнатах, исключение на пути ставки — с первой же ошибки, пауза event loop в
80 мс и подход комнаты к пределу — тоже.

Тем же файлом проверяются **формулы дашборда**. Ошибка в PromQL глазами не
видна: панель рисует правдоподобный график и молча врёт. Поэтому каждое
выражение, которое рисует дашборд, либо ссылается на проверенное записывающее
правило, либо имеет свой `promql_expr_test` с ожидаемым числом.

## Метрики и откуда взялись пороги

Пороги — не вкус, а трактовка **ОВ-2**: «≤15 мс = серверное время обработки
ставки; вещание ≤5 мс — время постановки в отправку». Порог связи 2 с и доля
40 % — из ТЗ §2.2, там же, где описан SLA Freeze.

| Метрика                                | Что меряет                                      | Порог      |
| -------------------------------------- | ----------------------------------------------- | ---------- |
| `auction_bid_duration_seconds`         | полный серверный путь ставки                    | p99 ≤15 мс |
| `auction_bid_core_duration_seconds`    | только атомарное ядро (Lua в Redis)             | —          |
| `auction_bids_total{outcome,code}`     | исходы ставок; `error` — исключение на пути     | 0 ошибок   |
| `auction_broadcast_duration_seconds`   | постановка события в отправку всем в комнате    | p99 ≤5 мс  |
| `auction_heartbeat_rtt_seconds`        | ответ на ping — качество связи зала             | 2 с        |
| `auction_gateway_connections`          | соединений на инстансе                          | —          |
| `auction_gateway_rooms`                | комнат на инстансе                              | —          |
| `auction_gateway_room_connections_max` | самая большая комната                           | 45 000     |
| `nodejs_eventloop_lag_p99_seconds`     | пауза event loop (стандартная метрика процесса) | 50 мс      |

**Ядро замеряется отдельно от полного пути** не для симметрии. Нагрузочный
прогон T-051 показал, что основной вклад дают три обращения в PostgreSQL ДО
ядра (проверка прав). С одной метрикой видно только «медленно» — с двумя видно,
что оптимизировать. На дашборде это отдельная панель: разница между линиями и
есть цена проверок.

**Метки лота нет ни у одной метрики.** Лотов десятки тысяч, а серия на каждый
лот — это отдельная временная серия на каждый бакет каждой гистограммы.
Операционные вопросы («укладываемся ли в SLA», «не растёт ли самая большая
комната») отвечаются и без разбивки, а разбор конкретного лота живёт в логах и
`audit_log`, где его id есть.

## Порт

Метрики отдаются на **своём порту** (`METRICS_PORT`, по умолчанию 9464), а не
ручкой `/api/metrics`. Причина не в эстетике: ingress публикует наружу весь
префикс `/api`, и ручка в нём означала бы, что размеры комнат, поток ставок и
разбивка отказов по кодам доступны любому желающему. Этого порта в ingress нет
вовсе — недостижимость снаружи обеспечена конфигурацией, а не проверкой в коде.

Отдают все три процесса: API, gateway и воркер. У воркера HTTP-слоя нет вовсе, и
без своего порта его метрики (перенос ставок, finisher, возвраты задатков) были
бы невидимы.

В Kubernetes порт один на все три — каждый живёт в своём поде. **На одной машине
задайте разные** (9464/9465/9466): процесс, которому порт занят, не поднимется, и
это правильно — молча оставшийся без метрик процесс на дашборде выглядит как
«всё спокойно». Браузерный стенд (`e2e/stack.ts`) так и делает.

## Чего здесь нет

**Живого Prometheus и Grafana.** Для них нужен кластер — это T-009, и он ждёт
инфраструктуру. Поэтому:

- правила и формулы дашборда проверены `promtool` фактически, с точными
  ожидаемыми значениями квантилей;
- наполнение метрик проверено e2e: ставка по сокету, вещание в комнату и ответ
  на ping приращивают ровно те счётчики, что должны (`gateway.e2e-spec.ts`);
- **дашборд глазами не видел никто.** JSON валиден, выражения проверены, но
  вёрстка панелей, единицы измерения и читаемость на живых данных — это то, что
  проверяется только импортом в Grafana. Пункт DoD «дашборд показывает p50/p95/p99
  в реальном времени» до кластера закрыт наполовину: числа считаются верно,
  показ не проверен.
