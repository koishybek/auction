# Нагрузочные сценарии (T-051/T-052, QA-01/QA-02/NFR-03)

## Что здесь

- `ws-hall.js` — зал торгов: масса зрителей на одном лоте, редкие ставки.
  Меряет две величины приёмки: задержку ответа на ставку и долю клиентов,
  получивших тики без пропусков.
- `seed-lot.ts` — готовит сцену: лот в идущих торгах и участников с задатками.
  Без него ставки отбивались бы проверкой прав, и замер мерил бы отказ гварда,
  а не работу ядра.
- `bid-race.ts` — гонка ставок: сто участников на один шаг одного лота, сто
  прогонов. Проверяет главный риск проекта (R-4): две принятые ставки на один
  шаг — это юридический спор о деньгах, а не расхождение счётчика.

## Как гонять

```bash
# 1. Собрать стенд и поднять контур (см. e2e/prepare.ts)
pnpm --filter @auction/e2e exec tsx prepare.ts
# api на 3110, gateway на 3210 — запускаются из apps/api/dist

# 2. Сцена
BIDDERS=40 pnpm --filter @auction/load seed

# 3. Прогон зала
VUS=500 RAMP=15s HOLD=25s BIDDER_RATIO=0.03 k6 run ws-hall.js

# Гонка ставок — отдельно, стенд ей не нужен (нужны Redis и собранный api)
pnpm --filter @auction/api build
pnpm --filter @auction/load race          # RUNS=100 BIDDERS=100 по умолчанию
```

Гонка ходит в базу `auction_test` — её создаёт `global-setup` e2e-тестов.
В свежем клоне сначала прогоните `pnpm --filter @auction/api test:e2e`,
иначе контейнер не поднимется: базы ещё нет.

## Гонка ставок: что измерено (T-052, QA-02)

Прогон 17.08.2026: 100 прогонов × 100 ставок × 2 сценария = 20 000 ставок.

| Показатель                 | Пачкой                 | По одной     | DoD                |
| -------------------------- | ---------------------- | ------------ | ------------------ |
| Принято ставок на прогон   | **1**                  | **1**        | ровно 1 ✅         |
| Отказов `PRICE_MISMATCH`   | **99**                 | **99**       | 99 корректных ✅   |
| Отказов с актуальной ценой | **99 из 99**           | **99 из 99** | «с актуальной» ✅  |
| Окно отправки, худшее      | **0 мс**               | 26.3 мс      | 100 ставок в 1 мс  |
| Прогон целиком, медиана    | 6.8 мс                 | 8.6 мс       | —                  |
| Ставок в outbox            | 220 = 200 + 20 прогрев |              | ни одной лишней ✅ |

Стабильно на 100 прогонах: харнесс валится на первом же отклонении, а не
усредняет его.

### Почему сценариев два

**Сто одновременных ставок с одной машины не отправить за миллисекунду.**
Ставка уходит в сокет отдельной записью, и сто записей из одного процесса
занимают ~26 мс — то есть первая ставка успевает выполниться задолго до того,
как уйдёт последняя. Гонка от этого не исчезает (все сто присылают одну и ту же
сумму, и лишний принятый был бы виден), но «одновременности в 1 мс» в таком
прогоне нет, и говорить, что она проверена, было бы неправдой.

Поэтому есть второй сценарий: все сто ставок уходят **одной отправкой в сокет**,
и ни одна из них не отправляется после того, как стал известен результат другой.
Окно отправки здесь ноль по построению, а не по замеру, — строже одной записи
одновременности с клиента не бывает. Тело каждой ставки собирает сам `BidService`
(`placementCall`), поэтому харнесс гоняет боевой путь, а не свою копию.

Чего этот сценарий НЕ утверждает: что Redis дождался всех ста команд, прежде чем
выполнить первую. Он выполняет их подряд из своего буфера, и порядок внутри
пачки нам неизвестен — да и неважен. Важно, что ни одна ставка не была
сформирована с оглядкой на исход другой: именно это отличает гонку от очереди.

### Что попутно нашлось

Отказ не называл актуальную цену. Проигравший в гонке узнавал её только из
широковещательного `bid_updated`, а клиент на всякий случай ещё и переспрашивал
снимок состояния — то есть **девяносто девять проигравших делали девяносто
девять лишних запросов ровно в самый нагруженный момент лота**. Теперь цену и
сумму следующей ставки приносит сам отказ; считает их тот же Lua-скрипт, что
отказал, поэтому это не стоило ни одного лишнего обращения в Redis — наоборот,
с пути отказа ушёл один round-trip, который раньше делался ради аудита.

## Зал торгов: что измерено фактически

Прогон 17.08.2026 на одной машине (ноутбук, Windows): генератор, API, gateway,
PostgreSQL и Redis делят один процессор.

| Показатель                         | 500 клиентов    | 60 клиентов   | DoD            |
| ---------------------------------- | --------------- | ------------- | -------------- |
| Клиенты без пропуска тиков         | **100 %**       | **100 %**     | ≥ 99.9 % ✅    |
| Снимок состояния при входе         | 100 % (499/499) | 100 % (60/60) | —              |
| Задержка ответа на ставку, медиана | 12 мс           | 11 мс         | —              |
| Задержка ответа на ставку, p95     | 38 мс           | 78 мс         | p99 ≤ 15 мс ❌ |
| Тиков принято                      | 19 569 (391/с)  | 1 884 (47/с)  | —              |

**Порог по задержке не пройден, и подгонять его я не стал.** Что при этом
важно понимать:

1. **Измеряется не то, что в DoD.** k6 меряет полный оборот: сеть, gateway,
   проверки прав, Lua, ответ. DoD говорит про «серверную обработку» — её видно
   только метриками внутри процесса, а их ещё нет (T-053).
2. **Узкое место — машина, а не код.** На 60 клиентах задержка ХУЖЕ, чем на
   500: там доля ставящих в восемь раз выше, и все ставки идут с одного адреса.
   Медиана в обоих прогонах ~11–12 мс, а хвост скачет — это картина
   конкуренции за процессор, а не постоянной стоимости пути.
3. **Конкретный след для оптимизации.** Путь ставки делает три обращения к
   PostgreSQL до атомарного ядра: пользователь, лот, задаток
   (`checkEligibility`). На нагрузке это и есть основной вклад. Лечится кэшем
   допуска в Redis с коротким TTL — тем же приёмом, что уже записан в
   CLAUDE.md для гварда авторизации.

## Почему 50 000 клиентов с этой машины не проверить

Каждое соединение стоит дескриптора и памяти на генераторе. На одной машине
раньше упрётся он, а не сервер, — и цифра получилась бы про ноутбук, а не про
систему. План это предусматривает («несколько генераторов»), и есть вторая
причина, найденная прогоном:

**лимит частоты считает по адресу** (FR-10: 1 ставка / 500 мс на IP). Все
виртуальные пользователи с одной машины делят один адрес, поэтому осмысленный
поток ставок с одного генератора ограничен двумя в секунду. Нагрузка по
ставкам без нескольких генераторов физически не собирается — это свойство
системы, а не стенда.

Что нужно для честного прогона 50k: 4–8 генераторов в той же сети, что stage,
и метрики сервера (T-053), чтобы отделить задержку сети от обработки.
