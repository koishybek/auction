# Нагрузочные сценарии (T-051, QA-01/NFR-03)

## Что здесь

- `ws-hall.js` — зал торгов: масса зрителей на одном лоте, редкие ставки.
  Меряет две величины приёмки: задержку ответа на ставку и долю клиентов,
  получивших тики без пропусков.
- `seed-lot.ts` — готовит сцену: лот в идущих торгах и участников с задатками.
  Без него ставки отбивались бы проверкой прав, и замер мерил бы отказ гварда,
  а не работу ядра.

## Как гонять

```bash
# 1. Собрать стенд и поднять контур (см. e2e/prepare.ts)
pnpm --filter @auction/e2e exec tsx prepare.ts
# api на 3110, gateway на 3210 — запускаются из apps/api/dist

# 2. Сцена
BIDDERS=40 pnpm --filter @auction/load seed

# 3. Прогон
VUS=500 RAMP=15s HOLD=25s BIDDER_RATIO=0.03 k6 run ws-hall.js
```

## Что измерено фактически

Прогон 17.08.2026 на одной машине (ноутбук, Windows): генератор, API, gateway,
PostgreSQL и Redis делят один процессор.

| Показатель                         | 500 клиентов    | 60 клиентов   | DoD            |
| ---------------------------------- | --------------- | ------------- | -------------- |
| Клиенты без пропуска тиков         | **100 %**       | **100 %**     | ≥ 99.9 % ✅    |
| Снимок состояния при входе         | 100 % (499/499) | 100 % (60/60) | —              |
| Задержка ответа на ставку, медиана | 12 мс           | 11 мс         | —              |
| Задержка ответа на ставку, p95     | 38 мс           | 78 мс         | p99 ≤ 15 мс ❌ |
| Тиков принято                      | 19 569 (391/с)  | 1 884 (47/с)  | —              |

**Порог по задержке не пройден, и подгонять его я не стал.** Что при этом
важно понимать:

1. **Измеряется не то, что в DoD.** k6 меряет полный оборот: сеть, gateway,
   проверки прав, Lua, ответ. DoD говорит про «серверную обработку» — её видно
   только метриками внутри процесса, а их ещё нет (T-053).
2. **Узкое место — машина, а не код.** На 60 клиентах задержка ХУЖЕ, чем на
   500: там доля ставящих в восемь раз выше, и все ставки идут с одного адреса.
   Медиана в обоих прогонах ~11–12 мс, а хвост скачет — это картина
   конкуренции за процессор, а не постоянной стоимости пути.
3. **Конкретный след для оптимизации.** Путь ставки делает три обращения к
   PostgreSQL до атомарного ядра: пользователь, лот, задаток
   (`checkEligibility`). На нагрузке это и есть основной вклад. Лечится кэшем
   допуска в Redis с коротким TTL — тем же приёмом, что уже записан в
   CLAUDE.md для гварда авторизации.

## Почему 50 000 клиентов с этой машины не проверить

Каждое соединение стоит дескриптора и памяти на генераторе. На одной машине
раньше упрётся он, а не сервер, — и цифра получилась бы про ноутбук, а не про
систему. План это предусматривает («несколько генераторов»), и есть вторая
причина, найденная прогоном:

**лимит частоты считает по адресу** (FR-10: 1 ставка / 500 мс на IP). Все
виртуальные пользователи с одной машины делят один адрес, поэтому осмысленный
поток ставок с одного генератора ограничен двумя в секунду. Нагрузка по
ставкам без нескольких генераторов физически не собирается — это свойство
системы, а не стенда.

Что нужно для честного прогона 50k: 4–8 генераторов в той же сети, что stage,
и метрики сервера (T-053), чтобы отделить задержку сети от обработки.
